# 国内工具分发与发布验收

本文说明 2026-10-07 新增源码的行为和迁移要求。本轮没有购买或部署云资源，没有更换在线目录或上传第三方安装包。`download.zhenxingai.com` 与 `download-backup.zhenxingai.com` 是预留的受信下载域名，写进白名单不代表 DNS、证书、对象存储、CDN或独立备源已经建成。

## 用户流程与分发边界

系统功能由客户端提供。第三方工具从自有目录选择与本机架构匹配的包；同一版本在主源和备用源保留同样的不可变文件。国内用户的受支持工具下载流程不应临时转去 GitHub 获取代码或安装包。

自有便携工具包、厂商安装器、应用商店软件、CLI及需要账户登录的软件有不同验收要求。本文新增的门禁只接受 `portable-zip` 和安全的 `.exe` 入口，不能用它的通过结果证明 MSI/EXE 安装器、软件登录、依赖下载或工具实际功能通过。没有可用包的条目仍是待补充/官方获取项，不能标记成“一键安装已验收”。工具转载许可与版权证据仍需人工审核，现有第三方发布审核脚本独立保留。

## 两个协议分开发布

旧客户端继续使用以下 v1 接口，格式、ETag和历史修订语义保持兼容：

| 类型 | v1 | v2 |
| --- | --- | --- |
| 公开目录 | `GET /v1/tools/catalog` | `GET /v2/tools/catalog` |
| 更新通知 | `GET /v1/tools/events` | `GET /v2/tools/events` |
| 私有管理读取 | `GET /v1/admin/tools/catalog` | `GET /v2/admin/tools/catalog` |
| 私有发布 | `POST /v1/admin/tools/publish` | `POST /v2/admin/tools/publish` |
| 本机管理页面 | `/admin/tools` | `/admin/tools-v2` |

本轮源代码已连接这些路由，v1未发布返回 `503`，v2尚未发布返回 `404`；未部署的新路由可能由旧服务/代理返回 `404`。新客户端的兼容行为必须覆盖这些状态，不能把“v2暂未发布”理解为清空 v1 已有工具。

两个协议分别存储在数据目录的 `tool-catalog/catalog.sqlite3` 与 `tool-catalog-v2/catalog.sqlite3`，各自保留 `catalogs`、`catalog_current`、`verification_receipts`。向 v2 发布不会切换 v1 指针；v1发布接口拒绝 v2 清单，反向也一样。来源URL的不可变绑定共同存储在 `tool-package-assets.sqlite3`，防止同一URL跨协议更换哈希或大小。回退时把已验收的旧内容作为更高的新修订发布，不能覆盖历史修订。

客户端保留全局递增修订，不能在同一修订号接受不同目录。因此首次v2发布还须大于当前v1修订及现客户端内置seed（目前revision 2）；生产Store在事务内强制这一条件。以后提升客户端seed时，应同步维护服务端初始修订下限，部署人员也须协调两份目录修订，而非把v2从1重新编号。

v1 包只含 `architecture/url/sizeBytes/sha256/entryPoint/kind`，禁止额外的 `mirrors` 字段，主地址仍只接受 `https://zhenxingai.com/downloads/tools/...zip`。v2 保留这些字段，另外必填 `mirrors:[]`，最多3个备源，加主源总计最多4个。v2允许主备使用以下3个准确的主机名：

- `zhenxingai.com`
- `download.zhenxingai.com`
- `download-backup.zhenxingai.com`

所有源须为 HTTPS默认端口 `/downloads/tools/` 下的安全ASCII ZIP路径，不得含凭证、查询、片段、转义、回溯。显式 `:443` 归一化；同一包的来源不能重复。同一版本只声明一份 `sizeBytes/sha256`，所有主备必须实际提供这一份相同字节。不同域名本身不能证明基础设施独立，部署时要另行确认存储、厂商账户与网络链路。

## 发布门禁已接入生产调用路径

管理员经过原有 Bearer 鉴权后，生产 `ToolCatalogStore.publish()` 先检查元数据、修订与不可变URL冲突，再调用 `verify_catalog_packages()`。验证流程包括：

1. 每个声明的准确URL完整GET一次；相同URL对应多个架构/入口时复用已读包，并逐一验证这些入口。
2. 不继承环境代理、cookie或管理员授权头。仅连接白名单域名，DNS结果必须全部为公共地址，连接固定到已检查的地址且TLS仍校验原主机名。所有重定向均拒绝。
3. 接受完整HTTP `200`；拒绝HTML/JSON/文本错误页、编码响应，检查Content-Length（存在时），实际字节数及SHA-256。不会用成功HEAD或ZIP头探测代替整包验证。
4. 检查ZIP首尾目录记录，遍历并读取所有条目到末尾核验CRC；拒绝Windows不安全路径、回溯、设备名、路径归一化、文件/目录碰撞、大小写重名、链接、reparse标记、特殊文件、加密及不支持的压缩方法。验证不解压到真实目录。
5. 检查声明入口存在且为支持的Windows PE可执行文件，PE架构须对应 `x64/x86/arm64`。`any`仍记录实际PE架构，不意味着它能在任意机器原生运行。此检查不执行工具，也不测试依赖完整性或工具功能。
6. 全部源通过后才产生回执。回执绑定经过严格校验和规范化的完整目录UTF-8字节、SHA-256、schema、revision、验收时间以及逐源字节数/哈希/文件数/展开量/入口架构/CRC。
7. 在SQLite写事务内重检修订和URL冲突，将回执、目录、全局URL绑定与当前指针一起提交；提交成功后才通知SSE。下载、哈希、CRC或入口失败时返回 `502`，当前指针及发布历史保持原状。

生产路径没有 `skipVerification`、信任本地缓存、接受客户端回执或“失败后照常发布”开关。CLI生成的回执用于审核，生产POST仍自行完整验收。相同修订的规范化内容已发布且存有匹配回执时，幂等重试复用原回执，不再下载；这不代表持续健康监测通过。旧数据库没有回执的历史修订仍可读取，但再次提交须真实验收后才能补回执，且不能倒退当前指针。

## 默认资源限制

| 限制 | 默认值 |
| --- | --- |
| 清单 | 最大4MiB、10000个工具 |
| 单ZIP下载 | 最大512MiB，并须严格等于声明大小 |
| 整目录所有唯一URL下载量 | 最大32GiB |
| 单ZIP条目数 | 最大10000，与客户端一致 |
| 单条目展开量 | 最大512MiB |
| 单ZIP总展开量 | 最大2GiB |
| DNS与网络请求/读取超时 | 15秒 |
| 单来源验收预算 | 180秒 |
| 整目录验收预算 | 1800秒 |
| 每Store并发发布请求 | 1个，多余请求返回503 |

预算在下载与条目读取中检查，单次阻塞读受请求超时约束，因此到达总预算后结束可能多出一个已开始的网络超时。一个私有临时目录依次保存一个源ZIP，成功后删除，失败也通过finally清理；不把整库全部压缩包留在本机，不执行EXE。标准库PE/ZIP结构校验不能替代杀毒、安全审计、人工许可审核或真实安装/启动验收。

## 本机审核命令与离线测试

在仓库根目录运行：

```powershell
python scripts/verify-tool-packages.py --catalog <待验收清单.json> --receipt <新的回执.json>
python -m unittest discover -s zxai-toolflow-server -p test_tool_catalog.py -v
python -m unittest discover -s zxai-toolflow-server -p 'test_*.py' -q
```

CLI只读取文件和自有下载来源，不发布清单；失败时退出码1且不写成功回执，成功时退出码0。已存在的回执不会被覆盖。`catalogSha256`绑定规范化目录，与生产存储及ETag一致，另有 `sourceFileSha256` 记录CLI输入原文件，避免把缩进/字段顺序变化误认为内容变化。

测试通过合成PE/ZIP、临时数据库与loopback假HTTP进行，生产HTTPS传输在测试里替换为本机HTTP，验证/发布逻辑仍真实运行。测试覆盖主备全部校验、HTML/重定向/编码响应、错长度/错哈希、非入口文件CRC、路径/链接/重名、入口/架构、资源上限、失败回滚、回执持久化、旧数据库迁移、跨schema URL不可变绑定、v1/v2独立读写与鉴权/SSE。合成PE不会执行，也不被作为真实可用工具发布。

## 部署迁移与尚未完成的外部条件

1. 备份当前数据目录。保留既有v1数据库；部署 `tool_catalog.py`、`tool_package_verifier.py`、`link_probe.py`、`server.py`及原服务依赖。只拷贝发布脚本不能接入门禁。服务启动时增加回执表，并迁移旧URL绑定到共享注册库，不删除当前目录，不自动发布v2。
2. 新增两个SQLite文件/目录需要数据目录可写。本实现使用磁盘上的共享主数据库与附加目录数据库，均采用DELETE回滚日志和FULL同步，使URL、回执、目录指针原子提交；备份/恢复时须把三份数据库作为一致整体。不要把注册数据库放到内存或网络文件系统。
3. 发布会真实读取全部工具源，可能需要数分钟；私有管理员通道的代理/客户端超时要允许完整验收，并确认服务器能直连自有HTTPS源。不要开放管理员POST到公众客户端，不能为绕过超时而关闭验收。无法直连或预算不足时发布会失败，现有目录继续提供。
4. 旧v1公开GET保持原代理白名单。v2公开catalog/events路由需单独配置，SSE禁止缓存和缓冲；管理员v2接口仍保持私有。部署源码不等于公网路由已经开放。
5. 两个国内主备域名需要真实DNS、TLS证书、国内存储/CDN及适用备案条件。两边须先持有经过许可和内容审核的同一完整文件，再声明到清单；不得把不存在的备源加进正式v2清单。
6. 当前线上目录不能仅凭历史metadata或部分ZIP头探测标为全部可用。应完整验收每个真实包，再补依赖/启动检查、国内电信/联通/移动网络测试和持续失败率监测。这些外部验收与云基础设施部署不在离线测试通过范围内。

本轮代码具备默认阻止未验收新修订发布的门禁，不能据此宣称“国内双源已上线”“所有工具都能安装”或“全国网络永远100%成功”。正式上线证据应包含真实来源验收回执、明确的待补充条目、网络与启动结果及独立备源部署记录。
